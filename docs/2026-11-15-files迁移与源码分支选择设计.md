# files/ 迁移与源码分支选择设计

日期：2026-11-15
范围：编译仓库（AN7581 / master / MT7981）+ PonWrt（master / bugfix）+ 两个 PON feed fork
决策来源：用户拍板「把本仓库里的 files 目录迁移至 ponwrt 仓库的 master 和 bugfix，这样就没有合并问题了，
至于工作流可以再重新优化流程，源码的分支也可以手动选择了，一举多得」

## 一、根因与目标

根因：固件工作流 `Load custom config` 步骤的 `[ -e files ] && mv files openwrt/files`。
`mv dir target` 在 target 已是目录时会把源目录**嵌进去**（变成 `openwrt/files/files/`，已实测），
而不是合并。ponwrt bugfix 分支自带 `files/`（2 个 WiFi 文件），于是编译仓库那份 overlay 必然落错位置。

目标：
1. overlay 的唯一来源是 ponwrt 源码树，编译仓库不再有 `files/`，那行 `mv` **直接删掉**（不是改成 cp——不需要合并了）。
2. 固件工作流可在运行时选 ponwrt 源码分支，用于验证 bugfix 的修复效果。
3. PON 两个修复从「补丁 + 应用脚本」改为「feed fork 里的真实提交 + 钉 sha」，取消应用脚本。

## 三、改动清单

执行顺序：A/B/D/E/F/G 是一条独立工作流（files 迁移 + 分支选择），不依赖 C；
C（feed fork）是另一条，被「用户建 fork 并给出 sha」阻塞。两条可分开落地、分开提交，
但 B 节的 `feeds.conf.default` 与删补丁必须等 C 完成，否则 bugfix 会同时失去修复与补丁。
先做 A/B/D/E/F/G 并跑一趟 master 验证迁移无回归，再接 C。

### A. PonWrt master（4 处）

| 文件 | 改动 |
|---|---|
| `.gitignore:16` | `/files` → 注释掉，照 bugfix 现有写法 `# /files - 自定义 files overlay 纳入版本管理` |

设备端 apk 解析 URL 会带上 `\r`。**落地顺序：先提交 `.gitattributes` 规则，再添加清单文件**，
否则规则生效前入库的 blob 仍带 CR。

注：bugfix 的 `.gitignore` 末尾无换行符，追加时先补一个 LF。

## 四、缓存 key 设计与已知取舍

**必须改的正确性问题**：现有 key `an7581-dl-<hashFiles('feeds.conf.default','an7581.config')>`，
两个哈希参数都取自**编译仓库**（根目录没有 `feeds.conf.default`，实际只有 `an7581.config` 参与），
所以 master 与 bugfix 算出的 key **完全相同**。`actions/cache` 精确命中只恢复不保存 →
后跑那条 lane 的新对象永远留不下来。插入分支段后两条 lane 各自独立。

`Clear` 步骤的前缀必须同步，否则勾了清理却一条都删不到、残留断言还照样通过（静默空转）。

**不加源码 sha 的取舍（决策 3）**：只带分支段时，同一分支内源码变了但 `an7581.config` 没变 →
key 不变 → 精确命中 → 不保存。即 bugfix 只有第一趟（或配置变更后第一趟）的对象能留住。
接受这个代价，因为**现成的 `clean_ccache` / `clean_dl_cache` 开关正好兜住**：
勾清理会删光本分支条目 → 本趟 miss → 收尾保存，等于手动强制重灌。
不需要为「机制失效」再加一层自动兜底。

**不留旧前缀 `an7581-dl-` 作 restore-key 兜底**：那样勾清理后仍会从旧条目恢复，冷编译不成立。
代价是改完后 master 与 bugfix 各有一趟全量重下 dl。

`gh cache list --limit 100` 保持不变（不加 sha 就不会每趟新增条目）。

## 五、Release 门控理由（决策 4）

标签名 `ImmortalWrt_<版本>_<设备>_<时间>` 不含分支，而 `Remove old Releases` 用
`delete_tag_pattern: _<device>_` + `keep_latest: 3` —— bugfix 发布会与正式版共用同一设备的 3 个名额，
可能把正式版删掉。门控到 master 后 bugfix 测试只出 artifact（`release` 本来默认关闭），
命名口径完全不变。若将来要让 bugfix 也能发布，需让标签带分支，那是命名口径变更，另议。

Release body 仍加源码溯源行（branch + sha），artifact 名与标签名不变。

## 十、flow_offloading_hw 核查结论：本来就默认开启

用户要求「flow_offloading_hw 在 fix 分支默认开启」。核查后确认**该状态已成立，两个分支都是，无需改代码**。

证据链：

1. `an7581.config:704` 为 `CONFIG_PACKAGE_firewall4=y`，`CONFIG_PACKAGE_firewall=`（firewall3）未选。
   台账原先读的 `package/network/config/firewall/files/firewall.config` 属 firewall3，**不进固件**。
2. firewall4 在 ponwrt 无 `files/` 目录，默认配置来自上游源码包：
   `PKG_SOURCE_URL=$(PROJECT_GIT)/project/firewall4.git`（`PROJECT_GIT=https://git.openwrt.org`）、
   `PKG_SOURCE_VERSION=e6f600c458bda7bc2d87b07e78fd06b50c9d7131`；
   `Package/firewall4/install` 是 `$(CP) -a $(PKG_BUILD_DIR)/root/*`，`/etc/config/firewall` 登记为 conffile。
3. 实测：浅克隆该提交到 `tmp/fw4check/firewall4`，按 quilt 排序依次
   `git apply --check` + `git apply` 两个补丁，**均通过**。应用后 `root/etc/config/firewall:9`
   为 `option flow_offloading_hw	1`（由 `001-firewall4-add-support-for-fullcone-nat.patch` 添加）。
   `001-add-bridge-flowtable-support.patch` 只改 `fw4.uc` 与 `ruleset.uc`，不碰默认配置，两者无冲突。
4. 两个补丁与 Makefile 在 master / bugfix 的 blob 完全相同
   （`0989908208791fe3237c139212fcdf859b3b4bc7` / `05e6c4dc82aaa0b30157de07b1862e27fda226d7` / `e410048f`）。
5. 覆盖点扫描为空：编译仓库 `set-firmware-defaults.sh` 与 `an7581.config`、ponwrt `files/`、
   `package/base-files/files/etc/uci-defaults/` 均无 firewall / flow_offload 写入。

**运行时前提**（验收要看这条）：`root/usr/share/ucode/fw4.uc:543` 的 `resolve_hw_offload_devices()`
先判 `default_option("flow_offloading_hw")`，再对解析出的物理设备试 `nft_try_hw_offload(devices)`；
硬件拒绝时打 warn `Hardware flow offloading unavailable, falling back to software offloading`
并把 `state.defaults.flow_offloading_hw` 置 false。
即：**配置为 1 不等于硬件卸载真的生效**，931/932 的效果要在该 warn 不出现的前提下验收。
消费点是 `ruleset.uc:25` 与 `:506` 的 `flags offload;`（后者正是 932 桥接卸载那条路径）。
